1. 인터넷의 탄생#

1.1 개요 — 왜 만들어졌나#

인터넷의 직접 조상은 1969년 미국 국방부 ARPA(고등연구계획국)가 만든 ARPANET이다. 흔히 “핵전쟁에 살아남기 위한 망"으로 설명되지만, 이는 절반만 맞다.

  • 연구 자원 공유가 1차 동기였다. 1960년대 컴퓨터는 대학·연구소마다 한 대씩 있는 값비싼 시분할(time-sharing) 기계였다. ARPA IPTO(정보처리기술실)의 리클라이더(J.C.R. Licklider)는 1962년 메모에서 이 기계들을 잇는 “은하계 컴퓨터 네트워크"를 상상했고, 후임 로버츠(Lawrence Roberts)가 이를 실제 프로젝트로 만들었다.
  • 생존성(survivability)은 패킷 교환 이론의 동기였다. RAND의 폴 배런(Paul Baran)은 1964년 『On Distributed Communications』에서 중앙 없는 분산망과 메시지 블록 교환을 제안했고, 영국 NPL의 도널드 데이비스(Donald Davies)는 독립적으로 같은 아이디어에 “패킷(packet)“이라는 이름을 붙였다(1965). UCLA의 클라인록(Leonard Kleinrock)은 큐잉 이론으로 패킷망을 수학적으로 분석하는 토대를 놓았다.

핵심은 회선 교환(circuit switching)에서 패킷 교환(packet switching)으로의 전환이다. 전화망은 통화 동안 회선을 독점하지만, 패킷망은 데이터를 잘게 잘라 각자 최선의 경로로 보낸다. 이 선택이 이후 모든 것을 결정했다.

개발 환경과 문화#

  • IMP(Interface Message Processor): BBN이 만든 최초의 “라우터”. 호스트 컴퓨터는 서로 다른 기종이라 직접 통신할 수 없었으므로, 각 호스트 앞에 동일한 소형 컴퓨터를 두어 패킷 처리를 맡겼다. 이 “호스트와 망을 분리한다"는 계층화 발상이 지금의 라우터·NIC 구조로 이어진다.
  • RFC(Request for Comments): 1969-04-07 스티브 크로커(Steve Crocker)가 쓴 RFC 1 “Host Software"가 시작. 대학원생들이 권위자를 자처하기 부담스러워 “의견을 구합니다"라고 이름 붙였다. 이 겸손한 이름이 열린 표준 문화의 뿌리가 되었고, HTTP(RFC 1945/2616)와 HTML 2.0(RFC 1866)도 RFC로 태어난다.
  • 네트워크 워킹 그룹(NWG): 상명하달이 아닌 합의 기반. 이후 IETF(1986)로 제도화된다. “We reject kings, presidents and voting. We believe in rough consensus and running code."(David Clark, 1992)

1.3 핵심 디자인 — TCP/IP와 종단 간 원칙#

ARPANET은 성공했지만 NCP는 ARPANET 내부에서만 통했다. 패킷 무선망(PRNET), 위성망(SATNET)이 생기자 서로 다른 망을 잇는(inter-net) 프로토콜이 필요해졌다.

  • 1973년 빈트 서프(Vint Cerf)와 밥 칸(Bob Kahn)이 TCP를 설계. 1974년 논문 『A Protocol for Packet Network Intercommunication』, 같은 해 RFC 675에서 “Internet"이라는 단어 등장.
  • 1978년 TCP를 TCP(신뢰성)와 IP(라우팅)로 분리. 이 분리로 UDP 같은 다른 전송 계층이 가능해졌다.
  • 1983-01-01 플래그 데이(Flag Day): ARPANET 전체가 NCP를 끄고 TCP/IP로 전환.
  • 1983년 폴 모카페트리스(Paul Mockapetris)의 DNS(RFC 882/883). 이전에는 SRI가 관리하는 HOSTS.TXT 파일 하나를 모두가 FTP로 받아 갔다.
  • 1983년 4.2BSD Unix에 TCP/IP 스택 탑재(빌 조이). 이 구현이 소켓 API(socket, bind, connect)를 정의했고, 오늘날 모든 OS의 네트워크 API가 이 형태다.

종단 간 원칙(end-to-end principle): 망은 단순하게(dumb pipe) 두고, 지능은 끝단(호스트)에 둔다. IP는 “최선을 다해 배달(best effort)“만 하고 순서·재전송은 TCP가 양 끝에서 처리한다. 전화망(똑똑한 망, 멍청한 단말)과 정반대의 설계이며, 이 덕분에 망을 바꾸지 않고도 웹, 음성, 영상 같은 새 응용이 끝단에서 얼마든지 태어날 수 있었다.

# 1983년 이후 인터넷의 계층 (TCP/IP 모델)

  응용   : HTTP, SMTP, DNS, FTP, SSH      ← 브라우저가 사는 곳
  전송   : TCP, UDP (그리고 2021년 QUIC)
  인터넷 : IP (IPv4 1981, IPv6 1998)
  링크   : Ethernet(1973 PARC → 1983 IEEE 802.3), Wi-Fi(1997), LTE ...

1.4 pros vs cons#

패킷 교환 + TCP/IP의 장단점.

  • 장점: 회선 효율, 부분 장애 내성, 이기종 망 연결, 끝단 혁신의 자유(허가 없는 혁신)
  • 단점: 실시간 보장 없음(지연·지터), 보안이 설계에 없음(IP 스푸핑, 평문), 주소 고갈(IPv4), 혼잡 제어를 나중에 덧댐(1988 반 제이컵슨)

2. 웹의 탄생#

2.1 개요 — CERN, 1989#

팀 버너스리(Tim Berners-Lee)는 CERN의 계약직 소프트웨어 엔지니어였다. 문제는 인터넷이 아니라 정보 관리였다. 수천 명의 물리학자가 서로 다른 컴퓨터, 서로 다른 문서 포맷으로 일하고, 사람이 떠나면 지식이 사라졌다.

  • 1980년 개인 프로젝트 ENQUIRE: 카드 사이를 링크로 잇는 하이퍼텍스트 도구.
  • 1989년 3월 『Information Management: A Proposal』. 상사 마이크 센달(Mike Sendall)의 메모: “Vague but exciting…”
  • 그가 결합한 기존 기술 세 가지: 하이퍼텍스트(테드 넬슨의 Xanadu, 더그 엥겔바트의 NLS, HyperCard), 인터넷/TCP/IP, SGML(문서 마크업 표준). 발명이라기보다 “조합"이었고, 그래서 이겼다.

버너스리는 1990년 가을, NeXT 컴퓨터 한 대(25MHz 68030, 8MB RAM, NeXTSTEP, Objective-C, Interface Builder) 에서 두 달 만에 아래를 모두 만들었다.

발명역할설계 원칙
URI/URL모든 자원에 전역 이름스킴(http:) + 호스트 + 경로. 기존 FTP, Gopher, 뉴스도 담을 수 있게
HTTP자원을 가져오는 프로토콜0.9는 GET /path 한 줄. 무상태(stateless). 텍스트 기반
HTML하이퍼텍스트 문서 포맷SGML 문법을 빌리되 극도로 단순하게. 링크(<a href>)가 핵심

여기에 소프트웨어 두 개:

  • WorldWideWeb (1990-12-25 첫 통신 성공): NeXT용 최초의 브라우저이자 편집기. 버너스리의 웹은 처음부터 읽기/쓰기(read/write)였다. 이 편집 기능이 이후 브라우저에서 사라진 것이 §5의 “authoring의 귀환” 이야기와 연결된다.
  • CERN httpd: 최초의 웹 서버. 첫 사이트 info.cern.ch.

1991년 니콜라 펠로우(Nicola Pellow)가 어떤 터미널에서도 도는 Line Mode Browser를 만들어 NeXT가 없는 세상에 웹을 퍼뜨렸다. 1991-08-06 alt.hypertext 뉴스그룹에 공개 발표. 1993-04-30 CERN이 웹 소프트웨어를 퍼블릭 도메인으로 공개 — 이 결정이 Gopher(1993년 라이선스료 발표로 몰락)와 운명을 갈랐다.

2.3 Mosaic — 웹이 대중의 것이 되다 (1993)#

  • 1992년 ViolaWWW(페이 위안 웨이), Erwise(핀란드), MidasWWW, Lynx(텍스트) 등 X11 브라우저가 등장.
  • 1993년 1~4월 NCSA(일리노이대)의 마크 앤드리슨(Marc Andreessen)과 에릭 비나(Eric Bina)가 Mosaic 공개. 같은 해 11월 Windows·Mac 버전. 성공 요인:
    1. 인라인 이미지 — 앤드리슨이 www-talk에 <img> 태그를 제안(1993-02). 버너스리는 문서의 순수성을 이유로 반대했지만 Mosaic은 그냥 구현했다. “구현이 표준을 이긴다"는 원칙이 처음 드러난 사례.
    2. 설치가 쉬웠고, Windows에서 돌았다.
    3. 클릭 가능한 링크, 뒤로 가기 같은 GUI 관례를 정착시켰다.
  • 1994년 앤드리슨과 짐 클라크(SGI 창업자)가 Netscape(초기 이름 Mosaic Communications) 창업. → §4

2.5 CSS의 역사#

문제: 초기 브라우저는 스타일을 사용자가 정했다(Mosaic 환경설정에서 <h1> 폰트를 고르는 식). 넷스케이프가 <font>, <center> 같은 표현 태그를 넣자 HTML이 오염되기 시작했다.

  • 1994-10-10 CERN의 호콘 비움 리(Håkon Wium Lie)가 『Cascading HTML Style Sheets』 제안. W3C의 베르트 보스(Bert Bos)가 합류.
  • 핵심 디자인: 캐스케이드(cascade). 저자·사용자·브라우저의 스타일이 충돌할 때 우선순위로 합친다. 이름의 “Cascading"이 바로 이것이다. 그리고 선택자로 문서 구조에 스타일을 매핑한다.
  • 경쟁안: 넷스케이프의 JSSS(JavaScript Style Sheets, 1996). document.tags.H1.color = "blue" 식. Netscape 4에만 실렸다가 사라졌다. 선언적(CSS) vs 명령적(JSSS)의 대결에서 선언적이 이겼다.
  • 1996-08 IE 3가 최초로 CSS 일부 지원. 1996-12-17 CSS1 W3C 권고. 1998-05 CSS2. 2011-06 CSS 2.1.
  • “CSS3"는 단일 스펙이 아니라 모듈(Selectors, Flexbox, Grid, Transforms…)의 묶음. 이후 버전 번호 대신 모듈별 레벨.
  • 2003년 CSS Zen Garden(데이브 셰이)이 “같은 HTML, 다른 CSS"로 분리의 가치를 대중에게 증명.
  • Acid1(1998), Acid2(2005), Acid3(2008) 테스트가 브라우저 간 호환성 경쟁의 상징이 됨.
  • 레이아웃 혁명: Flexbox(2009 초안 → 2012 안정), Grid(2017-03 Firefox 52·Chrome 57 동시 출시), 컨테이너 쿼리(202223), CSS 중첩(2023), :has()(202223).

2.6 JavaScript의 역사#

  • 1995-04 브렌던 아이크(Brendan Eich)가 넷스케이프에 입사. 임무는 “브라우저에 Scheme을 넣는 것”. 그러나 Sun과의 제휴로 Java처럼 보여야 한다는 조건이 붙었다.
  • 1995-05 10일 만에 프로토타입 Mocha 완성. 9월 Netscape 2.0 베타에 LiveScript로 탑재, 1995-12-04 Sun과의 공동 발표에서 JavaScript로 개명. Java와는 마케팅 외에 무관하다.
  • 설계 DNA: Self의 프로토타입 객체 + Scheme의 일급 함수·클로저 + Java의 문법 + (강요된) 느슨한 타입 변환. “디자인 실수"로 꼽히는 ==, with, 자동 세미콜론 삽입은 열흘이라는 일정과 Java 흉내의 대가다.
  • 1996-08 마이크로소프트가 역공학으로 JScript(IE 3) 출시. 호환성 지옥이 시작되자 넷스케이프가 표준화를 요청. 1997-06 ECMA-262 1판(ECMAScript). “JavaScript"는 Sun(현 Oracle)의 상표라 이런 이름이 됐다.

3. 브라우저 인터널#

참고: 이 절은 Chromium 기준이다. WebKit·Gecko도 단계는 같고 이름과 스레드 배치가 다르다.

3.1 개요 — 브라우저는 무엇을 하는 프로그램인가#

브라우저는 네트워크에서 받은 텍스트를 해석해 픽셀로 바꾸고, 사용자 입력에 반응하며, 신뢰할 수 없는 코드를 안전하게 실행하는 프로그램이다. 마지막 조건 때문에 OS와 닮아간다.

3.2 프로세스 모델#

Chrome(2008)이 가져온 첫 번째 혁신은 멀티 프로세스다. 탭 하나가 죽어도 브라우저는 산다.

  • 렌더러 프로세스는 샌드박스에 갇힌다. 파일도 네트워크도 직접 못 만지고 브라우저 프로세스에 부탁한다. 웹 페이지의 코드는 “신뢰할 수 없는 입력"이기 때문이다.
  • 사이트 격리(Site Isolation, Chrome 67, 2018): Spectre 이후 사이트마다 렌더러를 분리. iframe도 출처가 다르면 다른 프로세스로 간다.
  • 대가: 메모리. “크롬이 램을 먹는다"는 이 설계의 비용이다.

3.3 내비게이션 — 주소창 입력부터 응답까지#

  1. UI 스레드가 입력을 판단: 검색어인가 URL인가.
  2. 네트워크 서비스가 요청 시작: DNS 조회 → TCP 3-way handshake → TLS handshake → HTTP 요청. (HTTP/3 + QUIC이면 UDP 위에서 TLS와 전송을 한 번에.)
  3. 응답 헤더 도착: Content-Type 확인(없으면 MIME 스니핑), Safe Browsing 검사, 다운로드인지 렌더링인지 판단.
  4. 브라우저 프로세스가 렌더러를 준비(실제로는 2단계에서 미리 띄워 둠)하고 커밋(commit): 주소창이 바뀌고 히스토리가 쌓인다.
  5. 렌더러가 데이터 스트림을 받아 파싱 시작. load 이벤트까지 끝나면 내비게이션 완료.

3.4 렌더링 파이프라인 — 바이트에서 픽셀까지#

바이트 ─▶ 문자 ─▶ 토큰 ─▶ 노드 ─▶ DOM ──┐
                                        ├─▶ Style ─▶ Layout ─▶ Paint ─▶ Layerize ─▶ Commit
CSS 바이트 ────────────────▶ CSSOM ──┘         (스타일 계산)  (기하)   (그리기 명령)  (레이어)      │
                                                                                                    ▼
                                             ┌─ 컴포지터 스레드 ─────────────────────────────────────┐
                                             │ Tiling ─▶ Raster (Skia, GPU) ─▶ Draw Quads ─▶ Viz ─▶ 화면 │
                                             └───────────────────────────────────────────────────────┘

(1) 파싱 → DOM#

  • 토크나이저는 HTML 명세의 상태 기계(80여 개 상태). <를 만나면 “tag open state"로 가는 식이다.
  • 트리 빌더가 토큰을 노드로 만들어 DOM에 삽입. <p> 안의 <div> 같은 오류도 명세대로 복구.
  • <script>를 만나면 파싱이 멈춘다(JS가 document.write로 DOM을 바꿀 수 있으므로). async/defer/type=module이 이를 완화. 그동안 프리로드 스캐너가 앞을 훑어 이미지·CSS·JS를 미리 요청.
  • CSS는 렌더 차단: CSSOM이 완성되기 전엔 스타일 계산을 못 하고, JS도 CSSOM을 기다린다(getComputedStyle 때문).

(2) Style — 계산된 스타일#

  • 각 DOM 노드에 어떤 CSS 규칙이 맞는지 선택자 매칭(오른쪽에서 왼쪽으로 검사). 캐스케이드·상속·기본값을 합쳐 computed style.
  • Firefox의 Stylo(Servo에서 이식, 2017)는 이 단계를 Rust로 병렬화했다.

(3) Layout — 기하#

  • Layout 트리(render tree): display: none은 빠지고, ::before 같은 가상 요소는 들어간다.
  • 각 상자의 x, y, width, height 계산. 블록 서식 문맥, 인라인 서식 문맥, Flex, Grid, 테이블, 그리고 텍스트 줄바꿈·글리프 셰이핑(HarfBuzz).
  • Chromium은 2019~2021년 레이아웃 엔진을 LayoutNG로 재작성했다. 한국어처럼 단어 경계가 모호한 언어의 줄바꿈·IME 조합 구간 처리는 이 단계와 깊이 얽힌다.
  • Reflow: DOM/스타일이 바뀌면 다시 계산. 비싸다. JS에서 offsetHeight를 읽으면 브라우저는 강제로 지금 레이아웃을 계산한다(forced synchronous layout).

(4) Paint — 그리기 명령 목록#

  • “무엇을 어떤 순서로 그릴지”(display list / paint records)를 만든다. 아직 픽셀은 없다.
  • 순서는 stacking context(z-index, position, opacity, transform)가 결정.

(5) Layerize → Commit → Composite#

  • 일부 요소는 독립 레이어로 승격(transform, will-change, 비디오, 캔버스). 레이어를 따로 래스터해 두면 스크롤·애니메이션에서 다시 그릴 필요가 없다.
  • 메인 스레드가 레이어 트리를 컴포지터 스레드에 커밋. 이후 스크롤·transform 애니메이션은 메인 스레드가 JS로 바빠도 컴포지터가 혼자 처리한다. 이것이 “부드러운 스크롤"의 정체다.
  • 컴포지터가 레이어를 타일로 쪼개 래스터 워커가 Skia로 픽셀 생성(GPU 래스터). 그 결과를 draw quad로 묶어 GPU 프로세스(Viz)에 보내 화면에 합성.
// 성능의 핵심 규칙 세 가지를 코드로.
// (a) 레이아웃을 읽고 쓰기를 번갈아 하지 마라 — 강제 동기 레이아웃(layout thrashing)
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + "px"; // 읽기(레이아웃 강제) → 쓰기 → 다음 루프에서 또 강제
}
// (b) transform/opacity만 바꾸면 Layout·Paint를 건너뛰고 컴포지터에서 끝난다.
box.style.transform = "translateX(100px)";
// (c) 렌더링 직전에 실행되는 콜백은 requestAnimationFrame.
requestAnimationFrame(() => { /* 다음 프레임 직전 */ });

3.6 이벤트 루프#

JS는 단일 스레드다. 브라우저가 어떻게 “동시에” 네트워크·타이머·렌더링을 처리하는지가 이벤트 루프다.

loop:
  1. 태스크 큐에서 태스크 하나 실행 (클릭 핸들러, setTimeout 콜백, 네트워크 응답 처리...)
  2. 마이크로태스크 큐를 비울 때까지 실행 (Promise.then, queueMicrotask, MutationObserver)
  3. 렌더링 기회인가? (보통 60Hz, 디스플레이에 맞춤)
       → requestAnimationFrame 콜백 → Style → Layout → Paint → Commit
  4. 반복
  • 긴 태스크(50ms 초과)가 렌더링 기회를 뺏으면 화면이 멈춘다. Web Worker(2009)가 진짜 스레드를 주지만 DOM은 못 만진다.
  • 입력 이벤트는 컴포지터 스레드가 먼저 받는다. touchstart 핸들러가 있으면 메인 스레드에 물어봐야 해서 스크롤이 지연되었고, 그래서 { passive: true }가 생겼다.

  • 1995-05-26 빌 게이츠 메모 『The Internet Tidal Wave』: “인터넷은 1981년 IBM PC 이후 가장 중요한 변화다.” 마이크로소프트는 Spyglass에서 Mosaic 코드를 라이선스해 IE 1.0(1995-08, Windows 95 Plus! 팩)을 급조.
  • IE 3(1996-08): CSS, JScript, ActiveX. 처음으로 쓸 만해짐. IE 4(1997-10): Windows에 통합, DHTML. 출시 파티 뒤 마이크로소프트 직원들이 넷스케이프 잔디밭에 거대한 “e” 로고를 놓고 갔다.
  • 무기는 번들링이었다. Windows에 공짜로 딸려 오는 브라우저 vs 49달러짜리 넷스케이프. 1998-05 미 법무부가 US v. Microsoft 제소. 2000년 1심 “독점 남용” 판결, 분할 명령 → 항소심에서 취소, 2001년 화해. 브라우저는 이미 IE가 이긴 뒤였다.
  • 넷스케이프의 대응: 1998-01 소스 코드 공개(Mozilla). 하지만 Netscape 4 코드가 너무 낡아 엔진을 처음부터 다시 썼고(Gecko), 그 사이 2년 반의 공백이 치명적이었다. 1998-11 AOL이 42억 달러에 인수. Netscape 6(2000)는 실패작.
  • Opera(1995, 노르웨이 텔레노르 사내 프로젝트에서 출발): 유료 시절을 거치며 탭 브라우징 대중화(2000), 마우스 제스처, 스피드 다이얼(2007), 자체 엔진 Presto. 점유율은 작았지만 UI 혁신의 실험실. CSS의 아버지 호콘 비움 리가 CTO였다.

4.3 IE 6의 암흑기 (2001~2006)#

  • 2001-08 IE 6 출시 후 5년간 메이저 업데이트 없음. IE 팀은 사실상 해산. 점유율 95%.
  • 웹 개발자는 IE의 버그가 곧 표준인 세상에 살았다(박스 모델 버그, PNG 투명도, hasLayout).
  • 한국의 특수성: 1999년 전자서명법 → 공인인증서 → ActiveX 의존. IE가 한국에서 유독 오래 살아남은 이유. 이는 §7에서 말할 “브라우저에 네이티브 코드를 꽂는” 첫 세대 시도(ActiveX·NPAPI 플러그인·Java 애플릿·Flash)의 폐해이기도 하다.

4.4 2차 브라우저 전쟁 (2004~2012)#

  • Firefox 1.0(2004-11-09): Mozilla 스위트를 경량화한 Phoenix(2002) → Firebird → Firefox. 탭, 팝업 차단, 확장 기능, 표준 준수. 커뮤니티 모금으로 뉴욕타임스 전면광고. 2009~2010년 점유율 30% 돌파. IE를 깨운 것은 Firefox였다. IE 7(2006)이 5년 만에 나온 것은 Firefox 때문이다.
  • Safari(2003): 애플이 KHTML을 포크해 WebKit을 만들고 2005년 오픈소스화. 2007년 iPhone과 함께 “진짜 웹을 주머니에”. iOS는 2024년 EU DMA 전까지 모든 브라우저에 WebKit 사용을 강제했다(App Store 규정 2.5.6).
  • Chrome(2008-09-02): 스콧 매클라우드의 만화책으로 발표. 세 가지 무기:
    1. V8 — JS를 컴파일한다. Gmail이 갑자기 빨라졌다.
    2. 멀티 프로세스 + 샌드박스 — 탭이 죽어도 브라우저는 산다.
    3. 단순함 — 옴니박스(주소창=검색창), 탭이 위에, 크롬(UI 테두리)을 최소화. 이름 자체가 아이러니. 그리고 유통: Google 검색 첫 화면, 안드로이드 기본 탑재, Flash·Java 설치 프로그램에 끼워 넣기, TV 광고. 6주(2010) → 4주(2021) 고속 릴리스로 “버전"이라는 개념을 없앴다.
  • 2011년 말 Chrome이 Firefox 추월, 2012-05 IE 추월(StatCounter). 2차 전쟁 종료.
  • 2013-04-03 구글이 WebKit에서 Blink 포크. 같은 해 Opera가 Presto를 버리고 Chromium으로.
  • 2015 Microsoft Edge(EdgeHTML). 실패. 2018-12 Chromium 전환 발표, 2020-01-15 Chromium Edge. 2022-06-15 IE 11 지원 종료. “브라우저 전쟁의 승자가 패자의 엔진을 채택"한 역사적 순간.

  1. Ajax 시대(2004~): Gmail, Google Maps. “페이지"가 “앱"이 되다. Google Docs(2006, Writely 인수)가 오피스를 브라우저로. 2004년 팀 오라일리의 Web 2.0.
  2. HTML5 vs 네이티브(2010~2013): 스티브 잡스의 『Thoughts on Flash』(2010)가 Flash를 죽이고 HTML5를 밀었다. 그러나 2012년 저커버그가 “HTML5에 건 것이 최대 실수"라며 네이티브로 회귀. 모바일에서는 앱이 이겼다.
  3. WebAssembly 시대(2017~): Figma(C++ → WASM, 2016)가 “브라우저에서 도는 전문 도구"를 증명. Photoshop 웹(2021), AutoCAD 웹, Google Earth 웹, VS Code 웹(vscode.dev, 2021), StackBlitz WebContainers(Node.js를 브라우저 안에서, 2021).

5.3 브라우저가 장악한 것 (1) — 광고#

웹의 경제는 광고이고, 광고의 기술적 토대는 브라우저의 설계 결함에서 자랐다.

  • 쿠키(1994, 넷스케이프 루 몬툴리): 무상태 HTTP에 장바구니를 붙이려고 만든 것. 명세(RFC 2109, 1997)는 서드파티 쿠키를 기본 차단하라 권했지만 넷스케이프도 IE도 무시했다. 여기서 크로스 사이트 추적이 태어난다.
  • 1996 DoubleClick(광고 서버·추적), 2000 Google AdWords, 2007 구글의 DoubleClick 인수(31억 달러). 구글 매출의 75% 이상이 광고다. Chrome은 구글 광고 사업의 방어선이다.
  • 대응의 역사: AdBlock Plus(2006), uBlock Origin(2014), Safari ITP(2017, 지능형 추적 방지), Firefox ETP(2019), Brave(2016, 브렌던 아이크가 창업, 기본 차단 + BAT 토큰).
  • 구글의 딜레마: Privacy Sandbox(2019). 서드파티 쿠키 폐지를 2022 → 2023 → 2024로 미루다 2024-07 폐지 철회, 2025-04 “쿠키 유지” 확정. FLoC → Topics API. 그리고 Manifest V3로 uBlock Origin 무력화(2024~25).
  • 핵심 논점: 브라우저를 만드는 회사가 광고로 돈을 벌 때, 브라우저는 누구 편인가. Dia/Arc의 The Browser Company, Brave, Vivaldi, Ladybird의 존재 이유가 이 질문에 있다.

6.2 Dia 이전 — Arc의 성공과 한계#

  • Arc(2021 비공개 → 2023-07 macOS 공개 → 2024-04 Windows): 사이드바 탭, Spaces(작업 공간), 자동 탭 정리, Boosts(사이트 CSS/JS 커스터마이즈), Easels, Little Arc, Split View. Chromium을 Swift(ADK)로 감싸 “맥 앱처럼” 만들었다. 파워 유저와 디자이너 사이에서 컬트적 인기. 2023-10 Arc Max로 AI 기능(탭 요약, 링크 미리보기, 이름 자동 변경) 시도.
  • 2024-10 밀러의 영상 발표: Arc는 기능 완성 상태로 유지보수(보안·버그)만 하고, 회사는 새 브라우저에 집중.
  • 2025-05-27 『Letter to Arc members 2025』에서 밝힌 이유:
    1. Arc는 너무 달랐다. “novelty tax(새로움의 세금)” — 배우는 비용이 커서 파워 유저 너머로 퍼지지 못했다.
    2. 사용 데이터: 대부분의 사용자가 Spaces나 Boosts 같은 핵심 기능을 안 썼다.
    3. Arc를 오픈소스로 풀지 못하는 이유는 ADK가 Dia의 핵심 기반이기 때문. 팔지도 않는다.
    4. “AI는 앱이나 버튼이 아니라 브라우저 위에 세워진 새 환경이 될 것”. 새 제품은 처음부터 AI를 전제로 다시 짓는다.

6.4 pros vs cons#

장점#

  • 컨텍스트 무료 획득: 열린 탭과 히스토리가 곧 프롬프트. 별도 RAG 없이 개인화
  • 낮은 전환 비용: Chromium 호환, Chrome 확장, 익숙한 UI. Arc의 교훈을 반영
  • 프라이버시 포지셔닝: 광고 회사가 아니다. 히스토리 로컬 보관. (구독이 수익 모델)
  • 제품·디자인 역량: Arc로 증명된 UI 감각. 빠른 반복
  • Atlassian 인수로 자금·엔터프라이즈 유통 확보 (Jira·Confluence 사용자 30만 기업)

단점#

  • 플랫폼 소유자의 역습: Chrome+Gemini(2025-09), Edge Copilot Mode(2025-07), Safari. 기본 브라우저를 가진 쪽이 유리
  • AI 브라우저 난립: Perplexity Comet(2025-07), OpenAI ChatGPT Atlas(2025-10 출시 → 2026-08 종료, ChatGPT 앱·Chrome 확장으로 흡수), Opera Neon, Brave Leo. 차별점이 빠르게 상품화
  • 비용 구조: 모든 질문이 LLM 호출. 무료 사용자는 적자. Pro 20달러의 설득력
  • 신뢰: Arc를 2년 만에 사실상 중단. “Dia도 그러지 않을까”
  • 에이전트 브라우저의 보안: 프롬프트 인젝션(웹 페이지가 AI에게 명령). 2025-08 Brave가 Comet의 취약점을 공개. 브라우저가 “행동"까지 하면 위험도 OS 수준이 된다
  • Chromium 종속: 구글의 로드맵(MV3 등)을 따라야 함. 엔진 통제권 없음
  • macOS(Apple Silicon, 14+) 전용 출발. Windows는 2026년 가을 예정, 모바일·Linux 없음. 메모리·Skills 체이닝으로 RAM 사용 증가(8GB M1에서 30탭 이상이면 체감)
  • 인수 후 “지식 노동자용 업무 브라우저"로 초점 이동 가능성. 소비자 제품과의 긴장

6.5 향후 설계에 미친 영향과 현재 상황#

  • Dia가 제시한 “탭을 @로 참조하는 채팅”, “주소창=프롬프트”, “히스토리 기반 메모리"는 몇 달 안에 Chrome(Gemini 사이드 패널, 2025-09), Atlas(사이드 채팅 + 에이전트 모드), Comet(에이전트)에서 유사하게 나타났다. Arc의 사이드바 탭이 Edge·Brave·Zen에 복제된 것과 같은 패턴 — TBC는 발명하고 남이 유통한다.
  • 논쟁의 축이 이동했다: “AI 기능이 있느냐"에서 “브라우저가 사용자를 대신해 행동해도 되느냐(agentic)“와 “그 컨텍스트를 누가 보관하느냐"로.
  • 남는 질문: Dia는 브라우저인가, 브라우저 모양의 AI 클라이언트인가? 30년 전 넷스케이프가 “브라우저는 OS"라고 선언했을 때 마이크로소프트가 반응한 것처럼, 지금 구글·OpenAI·Apple이 반응하고 있다.

6.7 투자는 어떻게 받았고, 브라우저 전쟁 참전은 가치가 있었나#

어떻게 투자를 받았나 — 세 개의 지렛대#

  1. 이미 엑싯한 창업자: 밀러는 2011년 Branch를 에브 윌리엄스(Twitter)·조나 페레티(BuzzFeed)의 시드 약 200만 달러로 시작해 2014년 Facebook에 약 1,500만 달러에 팔았다. 아그라왈이 그 공동창업자다. 이후 백악관 최초의 Director of Product. “검증된 팀"이라는 시드 투자의 첫 조건을 갖췄다
  2. VC 안에서 태어난 회사: 백악관에서 형사사법 개혁 프로젝트로 Thrive Capital의 조시 쿠슈너와 알게 됐고, 퇴임 후 Thrive의 EIR → 정식 투자자가 됐다. Thrive 포트폴리오(Airtable, Slack, GitHub, Notion, Figma)를 심사하며 “다들 끝난 줄 알았던 소프트웨어 카테고리를 재발명하는데, 그 앱들이 도는 브라우저만 30년째 그대로다"라는 논지를 세웠다. 회사는 2019-09 Thrive 내부에서 인큐베이션됐고, 밀러는 2020년 코로나 봉쇄 2주 전에 Thrive를 나왔다
  3. “브라우저 위에서 회사를 세운 사람들"이 투자자: 시드 500만 달러(2020, Next Play Ventures = 제프 와이너 주도): 딜런 필드(Figma), 악샤이 코타리(Notion), 제이슨 워너(GitHub CTO). 시리즈 A 1,300만 달러(2021-05, Pace Capital 주도): 에릭 유안(Zoom), 패트릭 콜리슨(Stripe), 마이크 크리거(Instagram), 브렛 테일러(Salesforce), 리드 호프먼(LinkedIn), 냇 프리드먼(GitHub). 이들의 제품은 전부 브라우저 안에서 돈다. 브라우저가 나빠지면 자기 제품이 나빠지는 사람들이 브라우저 스타트업에 돈을 냈다

시리즈 B 5,000만 달러(2024-03, Pace Capital 크리스 파이크 주도, 기업가치 5.5억 달러). 누적 약 1.28억 달러.

투자 논지(크리스 파이크, Pace Capital): “브라우저는 운영체제가 되고 모든 소프트웨어는 웹앱으로 접근하게 된다.” 따라서 브라우저를 재발명하는 회사는 OS 자리를 노리는 회사다. 근거로 든 것은 Chrome 65%의 독점 아래 30년간 정체된 UX, 그리고 TBC의 주간 배포 속도였다. 수익 모델은 Superhuman식 구독, Perplexity 기본 검색 라이선스(2024-01 제휴), B2B 등을 “나중에 정한다"고 했다. 회사 스스로 “We might not make it"이라는 사이트를 열어 이 불확실성을 인정했다.

가치가 있었나 — pros vs cons#

  • 재무적으로: 1.28억 달러 투자 → 6.1억 달러 현금 매각(2025-09, 창업 6년). 시드·시리즈 A 투자자는 높은 수익을 거뒀다. 그러나 마지막 라운드(5.5억) 대비 10% 상승에 그쳐, 2024년 시리즈 B는 사실상 본전. VC가 기대하는 10배는 아니다. “실패"가 아니라 “독립 기업으로 끝까지 가지 못한 것”
  • 시장 구조로 보면: 넷스케이프 → AOL(1998), Opera → 중국 컨소시엄(2016), Firefox → 구글 검색 계약 의존, TBC → Atlassian. 브라우저 회사는 독립적으로 살아남은 적이 거의 없다. 검색·광고와 짝짓지 않으면 수익이 없고, 검색·광고는 구글과 싸워야 한다. 엔진(Chromium)은 못 바꾸고 셸/UX만 바꾸는 사업은 유통 없이는 파워 유저 너머로 퍼지지 못한다. Arc가 정확히 그 벽에 부딪혔다(novelty tax)
  • 전략적으로: 그럼에도 논지는 맞았다. Atlassian이 “직원 업무의 85%가 브라우저에서 일어난다. AI가 브라우저와 업무 계층을 재발명할 것"이라며 6.1억 달러로 그 논지를 샀다. Atlassian 내부에서 이미 수천 명이 Arc를 쓰고 있었다. OpenAI와 Perplexity도 인수를 검토했다
  • 카테고리 관점: AI 브라우저라는 카테고리를 TBC가 먼저 정의했고(Arc Max 2023 → Dia 2025), 그 뒤 Perplexity Comet, OpenAI Atlas, Chrome+Gemini, Edge Copilot이 따라왔다. 사이드바 탭이 Edge·Brave·Zen에 복제된 것처럼, 발명은 TBC가 하고 유통은 플랫폼 소유자가 한다
  • 창업자 개인으로: 두 번째 엑싯. 밀러는 Atlassian 안에서 Dia를 계속 이끈다. 자금·유통(30만 기업 고객)·보안/컴플라이언스를 얻은 대신 소비자 제품이라는 정체성은 잃었다(Atlassian: “소비자를 겨냥하지 않는다”)

결론#

투자를 받은 이유는 논지의 참신함보다 사람과 네트워크였다. 이미 한 번 판 창업자, VC 내부 인큐베이션, 그리고 브라우저 위에서 회사를 세운 창업자들의 엔젤 라인업. 논지(“브라우저 = OS”)는 넷스케이프가 1995년에 한 말과 같고, 그때도 지금도 맞았다.

참전이 가치 있었는지는 “누구에게"에 달렸다. 초기 투자자와 창업자에게는 그렇다. 후기 투자자에게는 간신히 그렇다. 독립 브라우저 회사라는 목표에 비추면 그렇지 않다. 브라우저 전쟁은 1995년 이후 한 번도 스타트업이 이긴 적이 없고, 이번에도 승자는 인수한 쪽과 기본 브라우저를 가진 쪽이다. 이 산업에서 스타트업의 현실적인 출구는 “카테고리를 먼저 정의하고 플랫폼 소유자에게 인수되는 것"이며, TBC는 그 출구를 정확히 통과했다.

7. 브라우저의 외적 확장#

7.1 개요 — 왜 브라우저를 앱에 넣는가#

브라우저가 OS라면, 브라우저를 통째로 앱에 넣으면 그 앱은 어디서나 돈다. 데스크탑 앱을 웹 기술(HTML/CSS/JS)로 만들되 파일 시스템·메뉴·트레이 같은 네이티브 기능을 붙이는 것. 이 발상의 계보:

시기기술방식
1996~ActiveX, NPAPI 플러그인, Java 애플릿, Flash브라우저 안에 네이티브 코드를 꽂는다 (반대 방향). 보안 재앙으로 2015~2020년 전부 퇴출
2008CEF(Chromium Embedded Framework, 마셜 그린블랫)Chromium을 C++ 라이브러리로. Spotify, Steam, Adobe 앱의 UI
2009PhoneGap/Cordova모바일 WebView에 웹 앱 + 네이티브 브리지
2011node-webkit(NW.js, 인텔 로저 왕)Node.js + Chromium을 같은 컨텍스트에서
2013Electron(GitHub, 청 자오)Atom 에디터를 위한 Atom Shell. Node.js + Chromium
2015PWA브라우저 자체가 앱 셸이 됨. 설치·오프라인·알림
2019Tauri(다니엘 톰슨-이베토, 루카스 노게이라)Rust + OS 내장 WebView

2020Microsoft WebView2Windows에 Chromium 기반 시스템 WebView 제공. Tauri가 Windows에서 쓸 만해진 계기

7.2 Electron — 핵심 디자인#

┌─────────────── Electron 앱 ───────────────┐
│  Main Process (Node.js)                    │  ← 창 생성, 메뉴, 파일, OS API. 앱당 하나
│     │ IPC (ipcMain / ipcRenderer)          │

}

        .run(tauri::generate_context!())

}
